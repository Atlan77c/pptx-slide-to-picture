# pptx-slide-to-picture

Librairie Java pour convertir une slide d'un fichier PowerPoint (`.pptx`) en image (PNG, JPEG ou SVG), en pur Java via [Apache POI](https://poi.apache.org/) (rendu raster) et [Apache Batik](https://xmlgraphics.apache.org/batik/) (rendu vectoriel SVG) — **sans dépendance à LibreOffice, à PowerPoint (automatisation COM) ni à un navigateur headless**.

## Installation

Le projet n'est pas encore publié sur Maven Central. En attendant, construisez le jar localement (voir [Build](#build)) et installez-le dans votre dépôt Maven local :

```bash
mvn install
```

Puis dans le `pom.xml` de votre projet :

```xml
<dependency>
  <groupId>io.github.Atlan77c</groupId>
  <artifactId>pptx-slide-to-picture</artifactId>
  <version>0.1.0-SNAPSHOT</version>
</dependency>
```

## Utilisation

```java
import io.github.atlan77c.pptx2picture.OutputFormat;
import io.github.atlan77c.pptx2picture.PptxSlideRenderer;
import io.github.atlan77c.pptx2picture.RenderOptions;

import java.awt.image.BufferedImage;
import java.io.File;

// Rendu direct vers un fichier PNG (slide n°4, index base 1) - format par défaut
PptxSlideRenderer.renderSlideToFile(new File("presentation.pptx"), 4, new File("slide4.png"));

// Ou récupérer l'image en mémoire pour la manipuler
BufferedImage image = PptxSlideRenderer.renderSlide(new File("presentation.pptx"), 4);

// Avec des options de rendu explicites
RenderOptions options = RenderOptions.builder()
    .scale(2.0f)             // résolution = taille native de la slide x 2 (défaut)
    .fixTextOverflow(true)   // corrige un débordement de texte connu (voir plus bas, défaut: true)
    .build();
PptxSlideRenderer.renderSlideToFile(new File("presentation.pptx"), 4, new File("slide4.png"), options);

// Rendu en JPEG (plus compact que le PNG, sans transparence)
RenderOptions jpegOptions = RenderOptions.builder()
    .format(OutputFormat.JPEG)
    .jpegQuality(0.9f)        // 0.0 (taille mini) à 1.0 (qualité max), défaut 0.92
    .build();
PptxSlideRenderer.renderSlideToFile(new File("presentation.pptx"), 4, new File("slide4.jpg"), jpegOptions);

// Rendu en SVG (vectoriel, net à n'importe quelle taille d'affichage)
RenderOptions svgOptions = RenderOptions.builder().format(OutputFormat.SVG).build();
PptxSlideRenderer.renderSlideToFile(new File("presentation.pptx"), 4, new File("slide4.svg"), svgOptions);
// ou récupérer directement le document SVG en mémoire :
String svgContent = PptxSlideRenderer.renderSlideAsSvg(new File("presentation.pptx"), 4, RenderOptions.defaults());

// Nombre de slides du fichier
int count = PptxSlideRenderer.getSlideCount(new File("presentation.pptx"));
```

## Fidélité du rendu et limites connues

Le texte, les formes vectorielles, les images et les tableaux natifs sont rendus fidèlement. Limites documentées :

- **Les graphiques intégrés (Excel / `XSLFChart`) ne sont pas rendus** par Apache POI — un espace vide apparaît à leur emplacement. C'est une limitation connue d'Apache POI (voir [BUGZILLA-60201](https://bz.apache.org/bugzilla/show_bug.cgi?id=60201)), pas de ce projet. Contournement envisageable (non implémenté ici) : extraire les données du graphique via l'API `XSLFChart`/`XDDFChart` et le redessiner séparément avec une bibliothèque de graphiques Java pure (ex. [JFreeChart](https://www.jfree.org/jfreechart/)).
- **Écart de métriques de police** : pour certaines polices, Java2D/AWT peut surestimer la hauteur de texte nécessaire par rapport au moteur de rendu natif de PowerPoint (jusqu'à ~30-35% observé dans certains cas — confirmé et quantifié précisément à ~30% sur un fichier réel via un diagnostic dédié, y compris pour une police custom correctement installée et correctement résolue par AWT sous son propre nom), ce qui peut faire déborder une zone de texte hors de sa boîte et chevaucher une forme voisine. **Corrigé par défaut** (`RenderOptions.fixTextOverflow(true)`, activé par défaut) en réduisant la police des formes concernées, différemment selon le mode d'ajustement automatique (`autofit`) configuré sur la forme dans le fichier source : les formes en retrécissement de police (`normAutofit`) ou en "redimensionner la forme selon le texte" (`spAutoFit`) sont systématiquement corrigées (dans les deux cas, PowerPoint ne montre jamais de vrai débordement, donc tout débordement mesuré ici est un artefact du calcul — voir note ci-dessous pour `spAutoFit`) ; les formes sans ajustement (`noAutofit`) ne sont réduites que lorsque le débordement chevaucherait réellement une autre forme de texte, pour rester fidèle aux chevauchements volontaires de l'auteur. Le retrécissement vise une hauteur cible légèrement sous la hauteur réelle de la boîte (marge de sécurité de 3%), pour absorber l'épaisseur du trait de bordure de la forme et un éventuel écart résiduel entre la mesure utilisée pour piloter le correctif et le rendu final — sans cette marge, un cas réel a montré un texte encore visuellement au ras de la bordure malgré une police fortement réduite. Désactivable via `RenderOptions.builder().fixTextOverflow(false)`.

  *Note sur `spAutoFit`* : dans PowerPoint, ce mode fait grandir la boîte plutôt que réduire la police — une première version de ce correctif reproduisait ce comportement en agrandissant la boîte, mais cela s'est révélé provoquer de nouveaux chevauchements avec les formes voisines sur des documents réels (l'agrandissement ne tient pas compte du reste de la mise en page). Réduire la police à la place laisse toutes les autres formes du slide à leur position d'origine : moins fidèle au mécanisme technique de cet autofit, mais plus fidèle au rendu global du diagramme.
- **Interligne en pourcentage (`<a:lnSpc><a:spcPct/></a:lnSpc>`) surestimé par Apache POI, indépendamment de la police et du gras** : pour un interligne déclaré en pourcentage, POI calcule la hauteur d'une ligne à partir des métriques réelles de la police (ascent/descent Java2D) plus un repli de +15% quand la police ne fournit pas son propre "leading" (cas fréquent) — un repli calé par POI sur LibreOffice/OpenOffice, pas sur PowerPoint (commentaire explicite en ce sens dans le code source officiel de POI). Or PowerPoint calcule cette même hauteur de façon totalement INDÉPENDANTE de la police et de la graisse effectivement utilisées, uniquement à partir de la taille de police déclarée (confirmé empiriquement par trois expériences isolant chacune une seule variable — gras, police, taille — sur un fichier de test dédié). Résultat sans correctif : un texte à interligne en pourcentage s'affiche plus aéré que dans PowerPoint, ce qui peut à la fois fausser l'aspect visuel et déclencher des rétrécissements/chevauchements superflus ailleurs dans le pipeline. **Corrigé par défaut** (même indicateur, `RenderOptions.fixTextOverflow(true)`) en recalculant l'interligne déclaré de chaque paragraphe concerné vers la valeur qui, une fois passée dans l'algorithme de POI, produit la hauteur de ligne attendue par PowerPoint (`hauteur = taille de police × 1,2`, valeur calibrée et validée sur deux tailles très différentes). Limite assumée : ne corrige pas la hauteur propre de la toute première ligne d'un bloc (jamais affectée par le pourcentage d'interligne dans l'algorithme de POI), et se cale sur le run de plus grande taille pour un paragraphe à tailles mixtes. Voir [`OverflowAwareTextFitter#correctPercentLineSpacingForFidelity`](src/main/java/io/github/atlan77c/pptx2picture/internal/OverflowAwareTextFitter.java).
- **Retour à la ligne trop tardif près du bord droit de la boîte, mot débordant visuellement du cadre** : Apache POI peut placer un point de retour à la ligne légèrement trop près du bord droit réel de la boîte, laissant alors le dernier mot d'une ligne déborder visuellement hors du cadre (ex. un mot débordant d'un encadré coloré) alors que PowerPoint l'aurait renvoyé à la ligne suivante — un écart de mesure Java2D/PowerPoint sur l'axe HORIZONTAL, distinct de celui documenté ci-dessus sur l'axe vertical. **Corrigé par défaut** (même indicateur, `RenderOptions.fixTextOverflow(true)`) via une détection différentielle : la hauteur de texte mesurée à la largeur réelle de l'ancre est comparée à celle mesurée à une largeur légèrement réduite (marge de sécurité générique) ; si cette réduction fait déjà basculer au moins un mot sur une nouvelle ligne, le point de retour à la ligne est considéré comme « à la limite », et la police est réduite progressivement jusqu'à ce qu'il ne le soit plus, plutôt que de laisser un débordement horizontal imperceptible au moment de la mesure mais visible au rendu. S'applique à toute forme dont le retour à la ligne automatique est actif, quel que soit son autofit. Voir `OverflowAwareTextFitter#isWrapMarginUnstable`.

  *Renfort spécifique au texte en gras* : sur un mot en gras, Apache POI peut en plus sous-estimer légèrement la largeur réelle du mot au moment de décider où couper la ligne (un biais indépendant de l'écart Java2D/PowerPoint ci-dessus). La marge de sécurité générique du garde-fou ci-dessus est alors augmentée, pour chaque run en gras, du surcroît de largeur réel mesuré entre ce mot en gras et le même texte dans la même police mais sans le gras — pour un texte sans aucun gras, cet ajout vaut 0 et le comportement redevient exactement celui du garde-fou générique seul. Voir `OverflowAwareTextFitter#maxBoldWidthPremium`.
- **Texte aligné à droite ou centré qui déborde entièrement de sa boîte et se superpose au texte voisin** (ex. un numéro de page aligné à droite juste avant le titre du chapitre suivant, dans un sommaire) : le masque de diapositive définit souvent, dans le style de corps de texte par défaut, un retrait de liste à puces à indentation suspendue (`marL`/`indent` négatif — le motif standard PowerPoint pour aligner la puce dans la zone de retrait et le texte à `marL`). Apache POI ne gère correctement ce retrait hérité que pour un alignement à GAUCHE, le seul cas où PowerPoint l'utilise réellement ; pour un alignement à DROITE ou CENTRE, ce même retrait perturbe le calcul de largeur utilisé par POI pour positionner le texte, provoquant un débordement de toute la largeur de la boîte vers la marge suivante — que le retrait soit hérité du masque ou recopié tel quel sur le paragraphe (une « matérialisation » automatique de PowerPoint, observée sur un fichier réel). **Corrigé par défaut** (non désactivable, sans effet sur le texte aligné à gauche) : pour tout paragraphe dont l'alignement résolu est DROITE ou CENTRE et dont `marL`/`indent` résolu est non nul, ces deux valeurs sont forcées à zéro avant le rendu — un retrait de liste à puces n'ayant de sens que pour du texte aligné à gauche. Voir [`RightAlignedIndentFixer`](src/main/java/io/github/atlan77c/pptx2picture/internal/RightAlignedIndentFixer.java).
- **Titre recouvert par une forme voisine** : le même écart de métriques de police décrit ci-dessus peut, même sans débordement mesuré, faire s'étendre légèrement plus bas le texte d'un titre que chez PowerPoint — suffisant pour le faire chevaucher une image ou une autre forme peinte juste après lui. **Corrigé par défaut** (non désactivable, sans effet sur les slides déjà correctes) en repeignant systématiquement chaque forme de titre par-dessus le reste de la slide une fois le dessin terminé. Un titre est reconnu soit via son type de placeholder OOXML (`title`/`ctrTitle`), soit — quand l'auteur l'a dissocié de son placeholder dans PowerPoint tout en gardant un nom explicite — via le préfixe de son nom, reconnu dans 5 langues : français (« Titre »), anglais (« Title »), espagnol/portugais brésilien (« Título »), italien (« Titolo ») et allemand (« Titel »). Pour reconnaître une langue supplémentaire, ajouter le mot correspondant à la liste `TITLE_NAME_PREFIXES` dans [`TitleRepainter`](src/main/java/io/github/atlan77c/pptx2picture/internal/TitleRepainter.java) (le nom à utiliser se lit dans le volet Sélection de PowerPoint pour une forme de titre dissociée de son placeholder, ou directement dans l'attribut `name` de `<p:nvSpPr><p:cNvPr>` du XML de la forme).
- **Texte plaqué en haut d'une forme non rectangulaire en mode « redimensionner la forme selon le texte » (`spAutoFit`), au lieu d'être centré verticalement** (ex. une zone de texte à laquelle un contour non rectangulaire — ellipse, forme libre... — a été appliqué via *Modifier la forme* dans PowerPoint) : pour une géométrie non rectangulaire, PowerPoint réserve, lors du calcul `spAutoFit`, une marge supplémentaire liée à la courbure de la forme (le texte doit rester dans la zone utile de l'ellipse, plus étroite près du haut/bas que sur un rectangle) — la boîte stockée dans le fichier est donc plus haute que ce qu'exigerait une mise en page purement rectangulaire du même texte. Apache POI, lui, mesure et positionne le texte comme un simple rectangle, sans jamais détecter de débordement (le texte tient dans cette boîte déjà plus haute que nécessaire) ; avec l'ancrage vertical par défaut OOXML (« Haut », quand le `bodyPr` n'en déclare aucun explicitement), tout l'espace résiduel se retrouve donc entièrement sous le texte, qui paraît poussé vers le haut. **Corrigé par défaut** (non désactivable, ne touche jamais un ancrage vertical explicitement choisi par l'auteur) en forçant l'ancrage vertical à MILIEU pour toute forme de texte `spAutoFit` dont la géométrie n'est pas un simple rectangle et dont le `bodyPr` ne déclare aucun `anchor` explicite — l'espace résiduel, quelle qu'en soit l'origine exacte, est ainsi réparti de part et d'autre du texte plutôt que laissé entièrement en bas. Voir [`RoundedShapeAnchorFixer`](src/main/java/io/github/atlan77c/pptx2picture/internal/RoundedShapeAnchorFixer.java).
- **Pointe de flèche mal orientée à l'extrémité d'un connecteur courbe ou coudé** (`curvedConnector2/3/4/5`, `bentConnector2/3/4/5`) : Apache POI calcule l'angle de la pointe uniquement à partir du rapport hauteur/largeur de la boîte englobante de la forme (`DrawSimpleShape.getHeadDecoration()`/`getTailDecoration()`), ce qui suppose implicitement que le connecteur EST la diagonale de sa boîte englobante — exact pour un connecteur droit (`straightConnector1`), faux pour un tracé courbe ou coudé, dont le trait entre et sort de chaque extrémité à l'horizontale ou à la verticale, jamais en diagonale. **Corrigé par défaut** (non désactivable, sans effet sur les connecteurs droits) en calculant l'angle réel à partir de la corde d'une portion du segment terminal du tracé proche de l'extrémité (15 % de sa longueur pour un tracé à un seul segment, 40 % pour un tracé à deux segments ou plus — une tangente Bézier instantanée s'est révélée dégénérer à l'horizontale/verticale sur les presets à ajustement par défaut), plutôt qu'à partir de la boîte englobante ; la position de la pointe est elle-même recalculée à partir du dernier point du tracé réel. La substitution passe par le point d'extension `Drawable.DRAW_FACTORY` de POI (un `DrawFactory` personnalisé remplace le dessinateur du connecteur sans jamais retirer la forme de la slide, préservant son ordre d'empilement — z-order — natif), combinée avec les autres correctifs basés sur le même mécanisme via [`DrawFactoryComposer`](src/main/java/io/github/atlan77c/pptx2picture/internal/DrawFactoryComposer.java) (le hint `Drawable.DRAW_FACTORY` ne retient qu'un seul `DrawFactory` à la fois). Corrige aussi, pour les pointes pleines (`TRIANGLE`, `OVAL`, `STEALTH`), un arrondi visible des sommets sur les petites pointes (`org.apache.poi.sl.draw.geom.Path` trace par défaut le contour d'une forme même quand seul son remplissage est voulu). Voir [`ConnectorArrowFixer`](src/main/java/io/github/atlan77c/pptx2picture/internal/ConnectorArrowFixer.java).
- **Image « découpée selon une forme » rendue intégralement rectangulaire** : une image insérée normalement puis recadrée sur une forme non rectangulaire dans PowerPoint (*Format de l'image > Rogner > Rogner selon la forme* — ellipse, forme libre...) ressortait, avant correctif, entièrement rectangulaire au rendu, recouvrant tout ce qui se trouve derrière elle dans la boîte englobante de son ancre. Cause identifiée dans le code source d'Apache POI lui-même (vérifié sur la version 5.2.5, celle utilisée par ce projet) : `DrawPictureShape` (le dessinateur POI dédié aux images) déclare volontairement n'avoir aucun remplissage propre (`getFillPaint()` renvoie toujours `null`), ce qui saute purement et simplement l'étape de `DrawSimpleShape.draw()` qui calcule et applique le contour géométrique réel de la forme — l'image est alors peinte telle quelle dans le rectangle englobant de son ancre, sans jamais être découpée selon ce contour. **Corrigé par défaut** (non désactivable, sans effet sur les images déjà rectangulaires — insertion normale, ou simple rognage rectangulaire classique `srcRect`) en calculant le contour géométrique réel de la forme et en l'appliquant comme clip avant de peindre l'image — voir [`PictureGeometryClipFixer`](src/main/java/io/github/atlan77c/pptx2picture/internal/PictureGeometryClipFixer.java).

  *Forme de découpe héritée d'un espace réservé, ou déclarée en contour libre (`custGeom`)* : une image insérée dans un espace réservé (« picture placeholder ») de la mise en page ne porte souvent aucune géométrie locale sur la slide elle-même — seul l'espace réservé correspondant du layout (voire du masque) déclare le `prstGeom`/`custGeom` de découpe, résolu par PowerPoint par héritage à l'affichage (slide → layout → master). `XSLFSimpleShape.getShapeType()`/`getGeometry()` n'inspectent, eux, que la forme locale — jamais cet héritage, contrairement à d'autres propriétés (couleur de remplissage, de trait...) déjà résolues par héritage ailleurs dans POI via `XSLFShape.fetchShapeProperty()`. `getShapeType()` renvoie en outre systématiquement `null` pour toute géométrie en contour libre (`custGeom`), locale ou héritée, la confondant avec une absence totale de géométrie. **Corrigé par défaut** en reproduisant explicitement la chaîne d'héritage de placeholder (`XSLFShape.fetchShapeProperty()`) avant de décider si une image doit être découpée, et en distinguant `prstGeom` local, `custGeom` local et absence de géométrie via `getGeometry()` (comparaison par identité à l'instance de repli partagée `"rect"`, plutôt qu'à `getShapeType() != null`, qui exclurait à tort tout contour libre) — la position/taille utilisée pour poser le clip reste toujours celle, locale, de l'image sur la slide ; seule la géométrie (le contour) peut venir d'un niveau hérité. Logique de résolution de l'héritage partagée avec le correctif suivant via [`PlaceholderGeometryResolver`](src/main/java/io/github/atlan77c/pptx2picture/internal/PlaceholderGeometryResolver.java).
- **Contour de remplissage d'une forme ORDINAIRE (texte ou forme automatique, pas une image) hérité d'un espace réservé jamais résolu** (ex. un rond devenu un carré, un panneau à sommet arrondi devenu un rectangle) : même cause racine que l'héritage de géométrie décrit ci-dessus pour les images, mais un mécanisme de contournement distinct — pour une forme ordinaire, POI ne saute pas l'étape de remplissage géométrique (contrairement à une image), mais `DrawSimpleShape.computeOutlines()` lit la géométrie via un appel local à la forme dessinée (`sh.getGeometry()`), qui ne suit jamais l'héritage de placeholder ; sans géométrie locale, `getGeometry()` retombe sur un simple rectangle, et le remplissage (couleur unie, par exemple) suit alors cette silhouette rectangulaire au lieu de la forme voulue. **Corrigé par défaut** (non désactivable, sans effet sur les formes à géométrie déjà locale — la quasi-totalité des cas, validé par comparaison pixel par pixel sur 54 slides de deux fichiers réels sans aucune différence détectée) en réimplémentant `computeOutlines()` pour utiliser la géométrie résolue par héritage de placeholder (même résolution que le correctif ci-dessus, partagée via `PlaceholderGeometryResolver`) à la place de l'appel local à la forme. S'applique à toute forme à corps de texte (zones de texte et formes automatiques, dessinées par POI via le même chemin `TextShape`). Voir [`AutoShapeGeometryFixer`](src/main/java/io/github/atlan77c/pptx2picture/internal/AutoShapeGeometryFixer.java).
- **Image rendue partiellement transparente dans PowerPoint (poignée « Transparence » du volet *Format de l'image*) ressortant entièrement opaque au rendu**, masquant tout ce qui devrait se voir en transparence derrière elle. Cause identifiée dans le code source d'Apache POI lui-même (vérifié sur la version 5.2.5) : `DrawPictureShape.drawContent()` ne lit jamais l'effet `<a:alphaModFix>` du `<a:blip>` de l'image — alors même que `ImageRenderer.setAlpha(double)`, la méthode qui permettrait de l'appliquer, existe déjà dans cette version. Ce manque est déjà corrigé côté Apache POI ([PR #990](https://github.com/apache/poi/pull/990), fusionnée le 17 janvier 2026), mais aucune version publiée à ce jour (la plus récente étant 5.5.1, du 30 novembre 2025) ne l'inclut encore. **Corrigé par défaut** (non désactivable, sans effet sur les images déjà pleinement opaques) en lisant directement `amt` sur l'`<a:alphaModFix>` du blip et en appliquant la fraction d'opacité correspondante via un `AlphaComposite` posé juste avant de peindre l'image — se compose avec la découpe ci-dessus plutôt que de s'y substituer (une image peut être à la fois recadrée selon une forme et semi-transparente). Voir [`PictureAlphaModFixer`](src/main/java/io/github/atlan77c/pptx2picture/internal/PictureAlphaModFixer.java).
- **Texte normal affiché comme une suite de symboles illisibles, ou un caractère isolé remplacé par un carré (glyphe absent)** : PowerPoint permet d'insérer un caractère spécial isolé (*Insertion > Symbole*, ex. une flèche dans la zone d'usage privé Unicode U+E000-U+F8FF) en posant une police symbole (`<a:sym typeface="Wingdings"/>`) sur le run correspondant ; PowerPoint sait n'appliquer visuellement cette police qu'au seul caractère symbole, mais Apache POI applique le `sym` à la TOTALITÉ du texte du run dès qu'aucune police latine (`<a:latin>`) explicite n'est présente — et comme les polices symbole font correspondre chaque lettre latine à un pictogramme (ou à rien du tout), tout texte normal qui se retrouve dans un run marqué `sym` s'affiche comme une suite de symboles illisibles, ou comme un carré (glyphe absent) pour un caractère sans correspondance. Le motif se présente sous plusieurs formes rencontrées sur des fichiers réels : un run unique mélangeant caractère symbole et texte normal accolé ; la police `sym` qui reste active sur plusieurs runs consécutifs jusqu'à la fin du paragraphe, y compris des runs sans aucun caractère symbole (ex. un mot isolé dans son propre run par la vérification orthographique de PowerPoint) ; et un run symbole isolé (l'espace précédant un mot) suivi d'un run normal totalement dépourvu de `<a:sym>`. **Corrigé par défaut** (non désactivable, sans effet sur les runs déjà correctement typés) en repérant, pour chaque paragraphe, le premier run problématique puis en reconstruisant toute la zone jusqu'à la fin du paragraphe : chaque run est redécoupé en segments symbole/texte normal (seuls les segments effectivement composés de caractères de la zone d'usage privé Unicode restent en police symbole), la police, la couleur, le gras et l'italique du run d'origine étant explicitement reportés sur chaque nouveau segment reconstruit. Parcourt aussi les cellules de tableau (`XSLFTable`), un type de forme distinct de `XSLFGroupShape`/`XSLFTextShape`. Voir [`SymbolFontRunFixer`](src/main/java/io/github/atlan77c/pptx2picture/internal/SymbolFontRunFixer.java).
- **Puces en police symbole (Wingdings...) rendues comme la lettre Latin littérale au lieu du pictogramme attendu** (ex. « Ø » au lieu d'une flèche, « q » au lieu d'une coche). Cause identifiée dans le code source d'Apache POI lui-même (vérifié sur la version 5.2.5) : pour dessiner une puce, `DrawTextParagraph.getBullet()` ne redirige le caractère de la puce vers la zone de glyphes symbole (décalage +0xF000) que si son `buFont` correspond **exactement** (insensible à la casse) à `"Wingdings"` ou `"Symbol"` — les deux seuls noms codés en dur dans `DrawFontManagerDefault`. Un `buFont` déclaré avec une liste de police de repli au format CSS (ex. `<a:buFont typeface="Wingdings,Sans-Serif"/>`, motif rencontré sur un fichier réel) ne matche ni l'un ni l'autre : POI peint alors le caractère comme du texte normal. **Corrigé par défaut** (non désactivable, sans effet sur les puces déjà correctement nommées) en normalisant `typeface` au nom exact seul dès que son premier élément (avant la virgule) correspond à `Wingdings`/`Symbol` — voir [`BulletSymbolFontFixer`](src/main/java/io/github/atlan77c/pptx2picture/internal/BulletSymbolFontFixer.java). Distinct de [`SymbolFontRunFixer`](src/main/java/io/github/atlan77c/pptx2picture/internal/SymbolFontRunFixer.java) (police symbole posée sur des runs de texte via `<a:sym>`, pas sur les puces de paragraphe). Limite assumée : les autres polices symbole Windows (Webdings, Wingdings 2/3, Marlett...) ne sont pas reconnues par POI pour ce remappage, même parfaitement nommées — non corrigées ici.
- **Ligne de texte à interligne en pourcentage anormalement haute, poussant le contenu suivant jusqu'à chevaucher une forme voisine indépendante** — même quand la forme concernée ne déborde jamais de sa propre ancre (donc invisible pour le correctif d'écart de métriques ci-dessus, qui ne compare une forme qu'à sa propre boîte). Cause identifiée sur un fichier réel : un paragraphe contenait un run entièrement blanc (un simple espace, résidu probable d'une ancienne mise en forme jamais nettoyée) dont la taille de police (48pt) dépassait largement celle du texte visible du même paragraphe (20pt) ; avec un interligne en pourcentage (`<a:lnSpc><a:spcPct .../></a:lnSpc>`, ou non déclaré), Apache POI mesure la hauteur de la ligne à partir de tous ses runs — espaces invisibles compris — gonflant démesurément cette ligne et décalant vers le bas tout le contenu placé après elle dans la même forme. **Corrigé par défaut** (non désactivable, sans effet sur les runs déjà de taille cohérente) en ramenant tout run entièrement blanc à la taille du plus grand run visible du même paragraphe, uniquement pour les paragraphes à interligne en pourcentage — un interligne en points absolus (`<a:spcPts>`) n'est pas concerné, sa hauteur de ligne ne dépendant pas des métriques de police. Voir [`OversizedWhitespaceRunFixer`](src/main/java/io/github/atlan77c/pptx2picture/internal/OversizedWhitespaceRunFixer.java).
- **Texte qui chevauche une forme voisine indépendante sans jamais déborder de sa propre ancre** — angle mort du correctif d'écart de métriques ci-dessus, qui ne compare une forme qu'à sa propre boîte : une zone de texte volontairement surdimensionnée (pour laisser de la place à une autre forme posée par-dessus, ex. une annotation) peut, à cause de la même surestimation Java2D/AWT déjà documentée, s'étendre réellement plus bas que chez PowerPoint et venir toucher cette forme voisine — tout en restant, dans les deux cas, à l'intérieur de sa propre ancre. Cause identifiée sur un fichier réel (comparaison directe avec une capture PowerPoint) : un bloc de statistiques empilant plusieurs paragraphes tenait largement dans une ancre haute de ~363pt (aucun débordement mesuré), mais chevauchait une annotation indépendante placée par l'auteur dans l'espace vide sous le dernier paragraphe. **Corrigé par défaut** (même indicateur que ci-dessus, `RenderOptions.fixTextOverflow(true)`) en deux temps : d'abord une réduction bornée de l'interligne des paragraphes concernés (jusqu'à 85 % de sa valeur d'origine — au-delà, rien ne garantit plus que deux lignes consécutives d'un même paragraphe ne se touchent pas, voir Javadoc de la classe), puis, seulement si cela ne suffit pas, un repli sur le rétrécissement de police déjà utilisé par le correctif ci-dessus (sûr par construction, puisqu'il réduit glyphes et interlignage ensemble). Si ni l'un ni l'autre ne suffit, la taille et l'interligne d'origine sont restaurés plutôt que de livrer un résultat partiel qui chevauche quand même. Voir [`NeighborShapeOverlapFixer`](src/main/java/io/github/atlan77c/pptx2picture/internal/NeighborShapeOverlapFixer.java).

  *Détection paragraphe par paragraphe (2026-08-28)* : une variante de ce motif a été constatée sur un autre fichier réel — une forme empilant plusieurs paragraphes ENTIÈREMENT VIDES (espaceurs volontaires, sans aucun texte) entre des paragraphes de texte réel, destinés à faire atterrir chaque paragraphe visible dans un espace libre précis pendant que des annotations opaques posées par-dessus couvrent le reste. Le bloc entier (espaceurs compris) chevauchait par construction plusieurs annotations à la fois — un chevauchement attendu et sans conséquence tant que seul du blanc s'y trouve réellement — rendant le test « forme entière » du correctif initial inopérant : il aurait fallu comprimer la totalité du bloc à un niveau qui aurait rendu tout le texte visible illisible, alors qu'un seul paragraphe posait réellement problème. Le test de collision distingue désormais chaque paragraphe individuellement et ignore les paragraphes entièrement vides (aucun glyphe peint, donc aucun risque visuel), sans changer le mécanisme de correction ni son périmètre (toujours la forme entière) — une généralisation strictement plus large que l'ancien test, qui ne peut donc jamais faire régresser le cas d'origine ci-dessus. La mesure de la hauteur individuelle de chaque paragraphe (aucune API publique POI ne l'expose) repose sur une copie de mesure jetable ; sa hauteur totale n'est toutefois jamais considérée comme fiable en valeur absolue - elle est systématiquement recalée sur `getTextHeight()` de la forme réelle (seule source de vérité), la copie ne servant qu'à répartir cette hauteur connue entre les paragraphes. Cette précaution a été ajoutée après qu'un premier essai, qui faisait confiance à la copie de mesure pour la hauteur totale elle-même, se soit révélé insuffisamment fidèle avec de vraies polices système lors des tests.

  *Bulles narratives (callouts) exclues de toute détection de chevauchement* : ce correctif, comme le garde-fou de chevauchement de titre plus haut, compare une forme à l'ANCRE ENTIÈRE de toute forme voisine candidate — pour une bulle de rappel (*Insertion > Formes > Bulles d'appel*, ex. "rectangle à coins arrondis"), cette ancre englobe géométriquement tout le tracé de la forme, bec compris, jusqu'à l'endroit qu'il désigne. Sans traitement particulier, une bulle dont le bec pointe vers un bloc de texte pouvait donc déclencher un rétrécissement de ce texte pour un chevauchement qui n'existe jamais visuellement dans PowerPoint (seul le bec, un simple trait, traverse la zone — jamais le texte de la bulle lui-même). Toute forme dont le type de géométrie PowerPoint appartient à la famille "callout" (`ShapeType.name().contains("CALLOUT")` — rectangles, ellipses, nuages, flèches de rappel...) est donc désormais exclue des deux côtés de toute détection de chevauchement entre formes distinctes : elle n'est jamais elle-même corrigée à cause d'une forme voisine, et jamais retenue comme obstacle pour une autre forme. Le débordement d'une bulle dans sa propre ancre reste traité normalement. Voir [`OverflowAwareTextFitter#isCalloutShape`](src/main/java/io/github/atlan77c/pptx2picture/internal/OverflowAwareTextFitter.java), partagée avec `NeighborShapeOverlapFixer`.
- **Texte d'une cellule de tableau natif qui déborde sur la cellule de la ligne suivante** : le même écart de métriques d'interligne en pourcentage documenté plus haut (repli +15% de POI vs. modèle réel `taille × 1,2` de PowerPoint) touche aussi les cellules de tableau — mais aucun des correctifs ci-dessus ne les corrige, car ils ne parcourent que les formes de texte autonomes et les groupes, jamais l'intérieur d'un `XSLFTable`. Or Apache POI fait grandir dynamiquement la hauteur de chaque ligne d'un tableau selon le texte mesuré de ses cellules (`XSLFTable#updateCellAnchor()`) — avec ce même écart de mesure non corrigé, une ligne peut ainsi être dessinée plus haute que chez PowerPoint pour un contenu identique, ou le texte peut déborder visuellement de sa propre ligne vers la suivante malgré cet agrandissement automatique. Cas réel à l'origine de ce correctif : une cellule à 3 paragraphes sans interligne déclaré localement (donc hérité, en pourcentage) débordait visuellement sur la cellule de la ligne suivante dans la même colonne. **Corrigé par défaut** (même indicateur, `RenderOptions.fixTextOverflow(true)`) en appliquant aux cellules le même correctif de fidélité d'interligne que pour une forme de texte autonome, puis, en tout dernier recours seulement si un résidu subsiste après cette correction, un rétrécissement borné de la police de la cellule (sans notion de collision avec une forme voisine, une cellule de tableau n'ayant pas d'équivalent de débordement volontaire). Voir [`TableCellLineSpacingFixer`](src/main/java/io/github/atlan77c/pptx2picture/internal/TableCellLineSpacingFixer.java).
- **Numérotation automatique (`<a:buAutoNum>`) incorrecte sur une liste à plusieurs niveaux d'indentation** (ex. un sommaire à 2 niveaux : les items de niveau 0 devraient former la séquence 1./2./3., et sous CHAQUE item de niveau 0, les items de niveau 1 devraient former leur PROPRE séquence indépendante recommençant à 1.) : avant correctif, tous les items de niveau 0 s'affichaient « 1. » et les items de niveau 1 poursuivaient une séquence plate au lieu de recommencer. Cause identifiée dans le code source d'Apache POI lui-même (vérifié sur la version 5.2.5) : `DrawTextShape.drawParagraphs(Graphics2D, double, double)` maintient un unique compteur `autoNbrIdx`, incrémenté pour CHAQUE paragraphe numéroté de la forme sans jamais lire `TextParagraph#getIndentLevel()` — un commentaire `// TODO: handle reset auto number indexes` dans le code source officiel de POI confirme la limitation, jamais corrigée depuis. Un `startAt` explicite posé sur un paragraphe (ex. « À partir de : 4 ») « fonctionne » en apparence par pur hasard de calcul (POI l'utilise comme valeur de repli du compteur plat), mais contamine dans la foulée, via ce même compteur partagé, la numérotation de tous les paragraphes suivants y compris ceux d'un niveau d'indentation différent. **Corrigé par défaut** (non désactivable, sans effet sur les listes à un seul niveau numéroté ou sans numérotation automatique) en réimplémentant `drawParagraphs()` avec un compteur PAR NIVEAU D'INDENTATION : chaque niveau reprend sa propre séquence, remise à 1 en cas de première visite ou de descente vers un niveau plus profond, et REPRISE (jamais redémarrée) en cas de retour vers un niveau déjà visité précédemment. Un `startAt` explicite n'agit lui que comme un PLANCHER sur cette séquence naturelle (`max(startAt, valeur naturelle)`), jamais comme un écrasement inconditionnel — corrigé le 2026-09-05 après qu'un fichier réel a révélé le cas : deux items de niveau 0 consécutifs avec le même `startAt="4"` doivent produire 4 puis 5 (le second `startAt` est déjà dépassé par la continuation naturelle du niveau, qui vaut 5 à ce point), pas 4 puis 4 comme le produisait un écrasement inconditionnel. La substitution passe par le même point d'extension `Drawable.DRAW_FACTORY` que les autres correctifs de ce type, composée via [`DrawFactoryComposer`](src/main/java/io/github/atlan77c/pptx2picture/internal/DrawFactoryComposer.java) ; les deux méthodes protégées de POI nécessaires à une réimplémentation fidèle de `drawParagraphs()` (`DrawTextParagraph#breakText`/`#setFirstParagraph`) sont invoquées par réflexion plutôt que par un package fractionné (« split package ») dans `org.apache.poi.sl.draw`, cette dernière approche cassant la résolution de module pour tout consommateur JPMS de cette librairie. Corrige au passage la mesure `getTextHeight()`, qui s'appuie sur le même `drawParagraphs()`. Limite assumée : la reprise (plutôt que redémarrage) d'un niveau déjà visité, et le comportement d'un `startAt` strictement inférieur à la continuation naturelle (ignoré par ce plancher) ou placé sur un paragraphe qui n'est pas le premier de son niveau, restent des hypothèses non vérifiées face à PowerPoint lui-même (l'OOXML ne spécifie pas formellement cette sémantique). Voir [`AutoNumberLevelFixer`](src/main/java/io/github/atlan77c/pptx2picture/internal/AutoNumberLevelFixer.java).
- **SVG : rendu du texte dépendant des polices installées chez le lecteur** — contrairement au PNG/JPEG (où les glyphes sont figés en pixels à la génération), le SVG produit des éléments `<text>` portant le nom de la police d'origine. Le résultat visuel final (empattement, chasse des caractères) dépend donc des polices disponibles sur la machine ou le navigateur qui affiche le fichier — s'assurer que les polices utilisées dans le `.pptx` source sont bien installées côté lecteur pour un rendu fidèle.

## Build

Nécessite un JDK 17+ et Maven.

```bash
mvn verify
```

Lance la compilation et la suite de tests (JUnit 5), sur des fichiers `.pptx` générés programmatiquement à la volée — aucun fichier `.pptx` externe n'est requis ni embarqué dans le dépôt.

## Comment ça marche

`XSLFSlide` (Apache POI) expose une méthode `draw(Graphics2D)` qui peint récursivement toutes les formes d'une slide. C'est la seule approche testée qui soit 100% Java et sans dépendance système lourde (contrairement aux wrappers LibreOffice/unoconv, à l'automatisation COM PowerPoint, ou aux rendus via navigateur headless type Puppeteer/Chromium). Le correctif de débordement de texte (voir ci-dessus) a été développé et validé itérativement sur des documents réels avant d'être porté dans cette librairie.

Pour le PNG/JPEG, `draw(Graphics2D)` peint dans un `Graphics2D` issu d'un `BufferedImage` (rendu raster classique). Pour le SVG, le même appel `draw(Graphics2D)` reçoit à la place un `SVGGraphics2D` fourni par [Apache Batik](https://xmlgraphics.apache.org/batik/) : cette classe implémente le même contrat `Graphics2D`, mais capture les instructions de dessin pour les sérialiser en SVG au lieu de peindre des pixels. Résultat : le même pipeline de rendu (y compris le correctif de débordement de texte, qui s'appuie lui aussi sur les métriques du `Graphics2D` fourni) produit indifféremment un raster ou du vectoriel, sans code dupliqué. Batik est publié sous licence Apache 2.0 — contrairement à l'alternative la plus connue pour ce besoin (JFreeSVG, sous GPLv3 ou licence commerciale), pleinement compatible avec la licence MIT de ce projet.
